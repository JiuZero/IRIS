# 规则插件开发指南

本文档描述 IRIS L3 规则引擎接受的规则文档格式，以及外部插件的安装方式。文中每一条都对着 `src/iris/rules/engine.py` 与 `src/iris/api/plugins.py` 的实现写：引擎的实际行为优先于本文档的措辞，两者不一致时以代码为准，并请回来改这份文档。

## 1. 插件是什么

规则是一份 YAML 文档，写明**在什么情况下**（`detect`）**做什么修复**（`actions`），以及**怎么确认修好了**（`post_action_verify`）。规则在仿真开始前对解包出来的 rootfs 目录逐条求值，匹配的动作直接改磁盘上的文件，或者攒成一段脚本交给仿真容器在启动时执行。

规则文档从两个目录读取，顺序即优先级：

| 目录 | 来源 | 可否通过界面卸载 |
| --- | --- | --- |
| `rules/` | 随 IRIS 源码分发，内置 6 条 | 否 |
| `<iris_home>/plugins/` | 外部上传安装 | 是 |

`iris_home` 默认是工作目录下的 `iris-home/`，可用环境变量 `IRIS_IRIS_HOME` 改。插件目录在它下面，所以**改这个变量会把已安装的插件一起带走**，这也是做隔离验证时唯一需要动的变量。

引擎不会执行插件里的任何代码。规则文档只能声明四类动作（写文件、正则替换、注释行、guest shell 行），没有表达式求值、没有循环、没有外部调用。`guest_shell` 是唯一一条把文本送进 guest 的通道，它的每一行都以受限用户身份在容器的 chroot 里跑，写在脚本里之前会被折成 ASCII。

## 2. 最小可用规则

```yaml
id: vendor-watchdog-guard
description: 厂商看门狗守护进程检测到硬件错误时会重启整机
stage: boot
detect:
  - file_regex: '::(once|respawn|restart):[^\n]*/(monitor|watchdog)'
    within: 'etc/inittab'
actions:
  - comment_lines:
      regex: '::(once|respawn|restart):[^\n]*/(monitor|watchdog)'
      prefix: "#IRIS-vendor-guard: "
```

`id` 是必填项，且格式受限，见 §4。`description` 会被插件中心卡片显示，写清楚**证据来源**比写清楚**做什么**有用。

## 3. 顶层键

顶层只接受这六个键，写错任何一个都会被安装器拒收，并在拒绝原因里逐个列出：

| 键 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 规则标识，见 §4 |
| `description` | 否 | 一句话说明，插件中心会显示 |
| `stage` | 否 | 默认 `boot`。**当前只用于记录与展示，不参与任何筛选**：所有规则对所有 rootfs 都会被求值 |
| `detect` | 否 | 匹配条件列表，留空等价于 `[{always: true}]` |
| `actions` | 否 | 修复动作列表 |
| `post_action_verify` | 否 | 修复后校验，见 §7 |

`stage` 不筛选这一点值得单独强调，因为字段名很容易让人以为写了 `stage: nvram` 的规则就只在 NVRAM 阶段跑。引擎不会这样读它：所有规则在每次 `apply_rules` 里都被完整求值。写 `stage` 只是为了让人读得懂这条规则打算解决哪个阶段的问题。

## 4. `id` 的格式

`id` 必须匹配 `^[a-z0-9][a-z0-9._-]{0,63}$`：首字符是小写字母或数字，其余可含小写字母、数字、点、下划线与连字符，长度 1–64。

约束来自两处现实：`id` 会落进 `repair_action` 表的 `rule_id` 列，也会出现在 CLI 的对齐表格里，所以大写字母与空格只会让这两处更难读。另外 `id` 决定落盘的文件名（`<id>.yaml`），允许路径分隔符会让一次上传写到目录外面去。

`id` 还必须**不与既有规则冲突**。内置规则优先，冲突的上传会被拒绝，而不是覆盖。运行期若仍发生冲突（有人手工往目录里塞文件），先到的那条保留，后到的记一条 warning 后跳过。

文件 stem 与 `id` 可以不同。内置 6 条规则恰好都以 `id` 命名文件，这是巧合而非约定；引擎不依赖它，上传的 `.yml` 也一律按 `id` 存成 `<id>.yaml`。

## 5. `detect`：匹配条件

`detect` 是一个列表，**顶层各条之间是「或」**：任意一条成立，规则就匹配。单个条件求值出 `(成立, 作用范围)` 两个值，范围决定文本类动作在哪些文件上跑。

### 5.1 叶子条件

| 条件 | 语义 |
| --- | --- |
| `always: true` | 无条件成立 |
| `path_exists: <路径>` | 该路径存在（不是符号链接）。目标若是目录，范围是它下面的全部文件 |
| `dir_nonempty: <路径>` | 该目录存在且非空 |
| `file_glob: <通配>` | 见下方警告 |
| `file_regex: <正则>` | 该正则能在某个文件里搜到内容，命中文件即范围 |

路径写相对 rootfs 的形式（`etc/inittab`、`opt/goahead`），前导 `/` 会被忽略，含 `..` 的路径会被拒绝。路径不支持符号链接：解包出来的 rootfs 保留 POSIX 符号链接，而在 Windows 宿主上 `stat()` 解析不了它们，所以「无法检查」与「不存在」被当作同一个答案处理。

**`etc/` 的自动回退。** 有些固件把 `/etc` 指向一个可写 overlay（`etc -> /var/etc`，盘上是空的），真正的文件树在只读的 `etc_ro/` 里，其 `inittab` 直接指名引用。这类固件上写 `etc/inittab` 描述的是一个不存在的文件，规则会静默永不触发。因此：路径以 `etc/` 开头且该路径确实不存在时，引擎会在 `etc_ro/` 下再找一次，找到就用那个。`within` / `file_glob` 里的 `etc/…` **同时**匹配两棵树，因为通配模式没有「是否存在」可测。

**`file_glob` 单独使用时恒成立。** 这是一个真实的坑：条件求值只要 `file_glob` 存在且路径合法就返回成立，文件是否命中体现在**范围**上，而范围为空不会让条件失败。所以单独写 `- file_glob: 'etc/passwd'` 的规则会在每个固件上匹配，只是无处可改。要用它筛选，请包进 `all:` 里与别的条件并列。

### 5.2 分组

```yaml
detect:
  - all:                     # 与（AND）
      - path_exists: 'etc/inittab'
      - any:                 # 或（OR）
          - path_exists: 'opt/monitor'
          - path_exists: 'bin/watchdog'
```

`all` / `any` 内部的键与叶子条件完全相同，可以继续嵌套。范围的处理规则：AND 组取各子条件范围的交集，交集为空时取最宽的一个（这样文本动作仍有地方可跑）；OR 组取并集。

### 5.3 修饰键

| 键 | 作用于 | 语义 |
| --- | --- | --- |
| `within: <通配>` | `file_regex`、`file_glob` | 把匹配限制在某个子树下 |
| `executable: true` | `path_exists` | 还要求该文件可执行 |

`executable` 在非 POSIX 宿主上**无法求值**：`os.access(X_OK)` 对每个普通文件都返回 True，Windows 上会让这个修饰符匹配一切。引擎选择不装样子——跳过该修饰符，并在规则上记一条告警。这也是为什么在 Windows 上传一条用到 `executable` 的插件会被拒收（安装要求零告警，见 §6）：在这个平台上它本来也不生效。

### 5.4 未知键

引擎对不认识的键是**记一条告警然后忽略**，这不是可以依赖的行为。历史上 `file_pattern`、`condition` 和 `post_action_verify` 就是在规则库里静静地躺着什么都没做。`all` / `any` 内部同样会被检查，包括嵌套更深的地方。

## 6. 安装：为什么会被拒

安装器（`POST /api/v1/plugins`）的校验在**碰磁盘之前**全部跑完，被拒的文件不会留下任何痕迹。校验链：

1. 大小不超过 1 MiB
2. 内容非空
3. 文件名不含路径分隔符，且不以 `.yaml` / `.yml` 结尾
4. UTF-8 可解码
5. YAML 语法正确
6. 顶层是映射
7. 有 `id`，且格式合法
8. 顶层、`detect`、`actions` 里的键全部在白名单内（含 `all` / `any` 内部）
9. `id` 不与既有规则冲突
10. 落盘为 `<id>.yaml`，**重新加载一次**
11. 重新加载的结果必须**零告警**

最后两条是关键。引擎自己的答案是「不认识就告警并忽略」，如果安装器只校验语法，那么一份把 `file_glob` 拼成 `fil_glob` 的文档会被报为安装成功，而它的条件永远不会被求值——用户看到「已安装」和一个不干活的插件。所以：**只要产生任何告警就拒绝安装，并把告警原文退回给作者。**

拒绝时返回 HTTP 422，`detail` 是写给插件作者的中文原因，原样包含引擎的告警文本。

内置规则不在插件目录里，因此无法通过卸载按钮移除，也无法被上传覆盖。

## 7. `actions`：修复动作

一条规则可以有多个动作，按声明顺序依次执行。每个动作只支持下面四种键之一。

### `write`：写一个文件

```yaml
actions:
  - write:
      path: etc/profile.d/iris.sh
      content: |
        export PATH=$PATH:/opt/goahead/bin
```

`path` 含 `..` 会被拒绝。父目录不存在时自动创建。

### `edit`：正则替换

```yaml
actions:
  - edit:
      regex: '\bmount\s+-t\s+jffs2\s+/dev/mtdblock\d+\s+/opt/app'
      replacement: '#IRIS: shadowed by empty partition\n#\g<0>'
      within: 'etc*/*'
```

在**匹配范围**内逐文件执行，按声明次数不限。跳过看起来是二进制的文件（含 NUL 字节），所以一个 `within` 开得很宽的规则不会把厂商 ELF 改坏。`within` 可以覆盖匹配范围。

### `comment_lines`：给行加前缀

```yaml
actions:
  - comment_lines:
      regex: '\bmount\s+-t\s+jffs2\s+/dev/mtdblock\d+\s+/opt/(app|custom|sav)'
      prefix: "#IRIS-shadow-fix: "
      within: 'etc*/*'
      max: 10
```

对匹配到的行插入前缀，保留原有缩进。已经以 `#` 开头的行不重复注释。`max` 默认不限。跳过二进制文件。

### `guest_shell`：交给容器在启动时执行

```yaml
actions:
  - guest_shell:
      - "mkdir -p /etc/scripts 2>/dev/null || true"
      - "chmod +x /opt/goahead/goahead 2>/dev/null || true"
```

这些行被攒起来写入 rootfs 里的 `/firmadyne/iris_rules.sh`，由仿真容器在启动时执行。设备节点、`/proc`、`/sys` 一类无法在宿主文件系统上完成的工作只有走这条路。

写入脚本前每一行会被折成 ASCII：脚本在 busybox `sh` 下运行，语言环境不可控，而之后读它的每个工具（`docker cp`、`grep`、一个用 `cat` 的人）都按**各自**的语言环境解码，一个误入的 `→` 或 emoji 会让整份文件在 GBK 宿主上不可读。装饰性字符被替换为 `?` 而不是让证据消失。

请在自己的命令里处理失败：加 `2>/dev/null || true`，或者自己判断返回码。这一层不做错误传播，脚本里一行失败不影响后面的行。

## 8. `post_action_verify`：修完怎么算好了

报告里写的必须是**验证过的事**，不是**尝试过的事**。校验在动作跑完之后重新读 rootfs，所以结论来自磁盘的真实状态。

| 键 | 语义 |
| --- | --- |
| `check_files` | 列表，每项 `path` 加 `must_exist` / `must_not_exist`（可同时给 `expected` 作为备注） |
| `forbidden_patterns` | 列表，每项 `pattern` 加 `in_file`，报告该模式是否仍出现在文件里 |
| `health_check` | `command` 加 `expected_exit_code`（默认 0），在**容器内**执行 |

```yaml
post_action_verify:
  check_files:
    - path: etc/scripts/iris_verify.log
      must_not_exist: true
  forbidden_patterns:
    - pattern: '\bmount\s+-t\s+jffs2\s+/dev/mtdblock\d+\s+/opt/(app|custom|sav)'
      in_file: etc/init.d/rcS
  health_check:
    command: '/opt/goahead/goahead -h'
    expected_exit_code: 0
```

`check_files` 与 `forbidden_patterns` 在宿主侧跑，含 `..` 的路径会被拒绝。`health_check` 必须在容器内跑（它要看活着的进程），所以它被渲染成与修复动作写进同一份脚本的一组命令，判定结果（通过或失败）都追加到 `/etc/scripts/iris_verify.log`，事后翻这一个文件就能看到全部结论。

## 9. 试一条规则

先干跑，确认作用范围对，再动手：

```bash
# 看看这条规则会做什么（默认干跑，不写盘）
python -m iris.cli rules apply /path/to/rootfs

# 确认无误后真正写入
python -m iris.cli rules apply /path/to/rootfs --apply
```

`rules apply` 输出机器可读的 JSON 报告，每条规则一条记录，含 `matched`、`detail`、`touched_files`、`warnings` 与 `verify`。**`matched: false` 且 `warnings` 非空**，通常意味着键拼错了或宿主平台不支持某个修饰键。

已安装的插件会一起被读到：

```bash
python -m iris.cli rules list
```

## 10. 排错

| 现象 | 原因 |
| --- | --- |
| 安装被拒，理由提到某个键 | 键名不在白名单里。引擎的白名单是 `iris.rules.engine` 里的 `RULE_KEYS` / `DETECT_KEYS` / `ACTION_KEYS` |
| 安装被拒，理由是告警原文 | 引擎加载时记了告警。照告警文本改，`all` / `any` 内部也算 |
| 安装被拒，理由是 id 冲突 | `id` 已被占用，包括与 6 条内置规则之一相同 |
| 规则永远不匹配 | 多半是 `path_exists` 指到了 `etc/` 下不存在的路径而该固件把文件放在 `etc_ro/`；引擎只回退一次，`etc_ro/` 也没有时就是不存在 |
| 规则匹配了但什么都没改 | 单独使用 `file_glob` 时它恒成立，范围却可能为空；或动作的 `within` 把范围收窄没了 |
| Windows 上含 `executable` 的插件装不上 | 该修饰符在无 POSIX 执行位的宿主上无法求值，引擎记告警，安装要求零告警 |
| 规则在 page 上显示了却没生效 | 页面读的是引擎会加载的规则集合，不是文档目录的目录列表；两者一致，出现这种不符说明引擎抛了异常，日志里有记录 |
