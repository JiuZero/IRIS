# 设计边界与技术限制

本文是 README「设计边界」六条之外的**细节展开**。README 保持"限制是什么 + 为什么这样取舍"
一句话的密度，具体机制、代码位置与实测对照放在这里，避免主叙事被工程细节淹没。

**本文的写法约定**：每一条先写"限制是什么"，再写"为什么这样取舍"或"当前停在哪一步"，
最后给出可复查的位置。凡是已经定位但**没有修**的问题，一律单独标注「未修」——
安全工具的能力描述里，一条被美化的记录比一条缺失的记录更危险。

---

## 1. 仿真通道能力不等价（arm64 ≠ MIPS/ARM32）

**限制**：arm64 通道不提供 libnvram 与 console 劫持。

**为什么**：MIPS / ARM32 走的是 FirmAE 已验证的**插桩内核**路线（定制内核 + `libnvram.so`
用户态 NVRAM 仿真 + console 劫持）。FirmAE 未发布 aarch64 插桩内核，IRIS 若要覆盖 aarch64
语料，只能在"不覆盖"与"换一条通道"之间选——选了后者：Alpine generic virt 内核 +
自建 initramfs，直跑厂商 `/sbin/init`。
后果是**依赖 nvram 的厂商服务在 arm64 下起不来**。这是通道取舍，不是缺陷；
代价换来的是 FirmAE 完全无法处理的 aarch64 语料（US TES7002 已经拿到 HTTP 302）。

**位置**：`scripts/emulate/build_arm64_initramfs.sh`、`scripts/emulate/get_arm64_assets.py`、
`binaries/Image.arm64`、`binaries/initramfs.arm64`。

## 2. 厂商网络模型强绑定真实存储

**限制**：厂商的网络配置依赖真实 flash 分区，仿真环境没有该分区时接口不获址。

**实例**：Tenda `configd` 依赖 `ubi0:ubi_Config` 挂载 `/var/config`，仿真环境无该分区时
eth0 不获址。由 `iris_net_fix` 兜底（补 IP、放行 iptables、telnetd:7002、goahead/boa Web 拉起），
US TES7002 实测由此拿到可达 Web。

**已知次级边界**：`iris_net_fix.sh` 通体基于 shell 函数，在 DIR-868L 这类
**ash 不支持函数定义**的厂商 BusyBox 上原理上跑不起来。
**不打算为此重写无函数版本**（成本极高，且该固件不需要兜底即可成功）——如实记录为能力边界。

**位置**：`scripts/emulate/iris_net_fix.sh`、`scripts/emulate/iris_net_fix_bg.sh`。

## 3. QEMU CPU 型号必须 `-cpu max`

**限制**：arm64 通道必须用 `-cpu max`。

**为什么**：厂商 aarch64 二进制常用 ARMv8.3 指针认证（PAC）指令，低版本 CPU 型号会 SIGILL。

**位置**：`src/iris/emulate/qemu_config.py`。

## 4. 架构白名单与 x86_64 的缺席

**限制**：可仿真架构只有 `armel / mipsel / mipseb / arm64`；**x86_64 语料不在仿真范围**。

**说明**：IRIS 的提取层能识别 `x64`（`iris-home/corpus/m0-baseline.toml` 有记录），
但没有 x86_64 的 QEMU 配置。FirmAE 同样不支持 x86_64 仿真——
**这一条是两侧共有的边界，既不是优势也不是劣势**。

**位置**：`src/iris/emulate/qemu_config.py`（`supported: armel, arm64, mipseb, mipsel`）。

## 5. 失败知识闭环：已读回，但只到"可读"为止

**现状**：`iris db cards` 按失败种类聚合 `failure_profile`，能读出该类失败出现在多少次 run、
哪些镜像、哪些架构、最后一次何时，以及这些 run 上实际触发过哪些 L3 规则；
`--promote-only` 只保留最近若干次失败 run 里仍在出现的种类，即"还需要写规则的清单"
（`network-fallback-ok` 这类信息类被排除，因为它表示兜底**正常工作**）。

**边界**：**不会**据此自动施加修复。一条规则有效的唯一证据是活体运行上的 `post_action_verify`，
"被记住的成功"不算。

**剩余限制（未修）**：

- `repair_action` 此前有表无写入路径，现已由 `emulate_firmware` 落库；
- 但 `RuleReport.touched_files` **不落库**——`prepare_from_firmware` 只保留命中的 rule id，
  因此无法回答"这次修补动了几处"；
- 卡片上的 `recovered` 目前恒为 0，因为历史上没有任何成功 run 带过失败行。

**位置**：`src/iris/db/knowledge.py`、`src/iris/monitor/ledger.py`。

## 6. 链路探测：只在失败路径上，且有一层测不准

**限制**：`iris.emulate.linkprobe` 分层实测 route / ARP / ICMP / service 并产出链路分层表，
**只在 Web 超时的失败路径上运行**——成功路径不做探测。这是有意为之，
不是遗漏：只有需要解释失败时才付探测的代价。

**测不准的那一层**：ARP 层在没有邻居表条目时**无法区分「没有这个地址」与「ARP 问过但没人应」**，
此时该层记 `unknown`，verdict 的 `detail` 会显式写出"哪一层没测到"。

**落库口径**：四层状态与首个断点会落库（`probe` / `first_break` / `table` 三键），
但**每层原始探测文案与"探测不可用"原因不落库**。

**位置**：`src/iris/emulate/linkprobe.py`、`src/iris/failures.py`、`web/src/pages/InstanceDetail.tsx`。

## 7. guest 文件系统：能直接读写，但值守用不上

**能力**：`iris guest ls/get/put` 在特权容器内对 guest 镜像做 loop 挂载（与 `make_image.sh`
构建期同一操作），`guest put` 注入的代码会在下次启动被 guest 执行
（2026-10-04 DIR-868L 实测：串口出现注入的 `IRIS-REPAIR-PROOF`，Web 仍 HTTP 200）。

**两条边界**：

1. 看到的是**磁盘上的文件**，不是运行中 guest 的视图（内存缓冲、被挂载覆盖的路径都不算）；
2. 访问状态盘要求 **QEMU 已停止**，而值守的动作都发生在它运行时，
   所以值守侧的 `n=0` 依旧被读作 UNKNOWN。

**位置**：`src/iris/emulate/guestfs.py`。详见 `docs/10-AI值守与稳定性治理.md` §6.4 与 §9。

## 8. 运行期写入与宿主观测（已改善）

**现状**：`run_qemu.sh` 改用持久的 `state.raw`（出厂镜像 `image.raw` 保持不动，
可随时 `iris guest reset <iid>` 回到出厂状态），guest 与修补的写入能跨启动保留。

首启从串口认出 guest 自己的子网后，该地址会被写进 `/work/scratch/<iid>/guest_ip`
（与 `arch` 标记同目录），`run_qemu.sh` 重跑时优先读它，`WEB_SERVER_RESTART`
因此不再退回 `192.168.1.254/16` 的默认桥地址。

**对照实测**（2026-10-04 DIR-868L，同一容器、同样三参数重跑）：
有标记时桥为 `192.168.0.254/16` 且 `HTTP 200`；把标记挪走作对照则是
`192.168.1.254/16` 且 `HTTP 000`。

**边界**：标记里的地址不是四段十进制就退回默认，而不是让启动失败；
`make_image.sh` 重烤镜像时会连同 `state.raw` 一起删掉它。

**本次交付轮复现**：2026-10-06 实跑 DIR-868L 得到 `HTTP 200 @50.2s`，
日志中可见宿主先落在 `192.168.1.254/24`，随后在 guest 子网内重新落点
`192.168.0.254/24` 并建立转发。

## 9. 架构判定：`inspect` 与 `emulate` 不一致（**未修**）

**现象**：同一份 US 版 TES7002（裸 squashfs，offset `0x43100`，无 uImage），
`iris extract inspect` 报 `arch: mipsel`，`iris emulate run --arch auto` 却用 arm64 跑出 HTTP 200。

**根因**：`src/iris/extract/firmware.py` 的 `_infer_arch()` 有四级兜底，
第四级把 squashfs 容器端序当成通用兜底——而 squashfs 端序只描述容器元数据的字节序，
与 guest 架构无关（aarch64 小端 ABI 打出的 rootfs 同样是 `hsqs`）。

**影响面**：`/pipeline` 路径会对这份固件真实报 `arch-mismatch`；`extract add --no-verify`
会把错误 arch 写进 `firmware` 表；`tests/test_firmware.py` 里有一条测试把这个错误行为固化成期望值。

**为什么这轮不修**：它要动 5 个消费方 + 重写一条把错误行为固化成期望值的测试，
属于独立一轮的工作量；混在数据采集轮里改会让 `docs/08` 的实测数字失去可追溯性。

**正确表述**：这一条与 FirmAE 的对照**不能**被表述成"IRIS 的架构处理更严谨"——
IRIS 的 `inspect` 在同一份固件上也判错了。差别只有一条：
**IRIS 的判定链上多一个能判对的第二证据源**（解压后 ELF census，639/640 命中 aarch64），
而 FirmAE 的 `getArch.py` 只有 tarball 扫描这一条路。

**位置**：`docs/08-与FirmAE对比.md` §9.1 与 §9.2。

## 11. 语料规模

当前 **9 台有效语料**（10 台语料剔除 1 份 GPON 残包）。这个规模支撑得起
"逐台对照 + 失败根因定位"，但**离任何可承诺的成功率都还很远**——
对外只报能力口径 + 明示分母，不做成功率承诺。
