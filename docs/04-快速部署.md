# 04 · 快速部署与迁移

本文件覆盖 IRIS 从零部署、离线迁移到冒烟验证的完整流程。目标机器与本机同架构（x86_64 Windows / Linux，需 Docker Desktop 或 Docker Engine）。

## 0. 前置条件

| 组件 | 要求 | 校验命令 |
|---|---|---|
| Python | ≥ 3.11 | `python --version` |
| Docker | Desktop（WSL2 后端）或 Engine，需 `--privileged` 权限 | `docker info` |
| 磁盘 | ≥ 10 GB（镜像 + rootfs 工作区） | — |
| 网络 | 首次构建需访问 apt 源与 dl-cdn.alpinelinux.org | — |

## 1. 在线安装（5 分钟）

```bash
git clone <repo-url> IRIS && cd IRIS

# Python 侧
python -m venv .venv
.venv\Scripts\activate          # Windows；Linux 用 source .venv/bin/activate
pip install -e ".[dev]"         # 不要 pip 全局安装，避免污染宿主环境
iris db init                    # 创建 iris-home/iris.db 元数据表

# Docker 侧（两条镜像，顺序构建）
docker build -t iris-emulate:latest        -f docker/emulate/Dockerfile      .
docker build -t iris-emulate-baked:latest  -f docker/emulate/Dockerfile.baked .
```

`Dockerfile.baked` 只做了两件事：把 `binaries/`（内核、busybox、libnvram 等）和 `scripts/emulate/`（make_image.sh / run_qemu.sh 等）复制进 `iris-emulate`。因此**任何脚本或 assets 改动后必须重建 baked 镜像**，否则仿真容器里跑的还是旧版：

```bash
docker rmi -f iris-emulate-baked:latest
docker build -q -t iris-emulate-baked:latest -f docker/emulate/Dockerfile.baked .
```

## 2. 一键离线迁移（无外网目标机）

在已部署好的机器上导出，目标机只需 Docker + Python：

```bash
# 源机
docker save iris-emulate:latest iris-emulate-baked:latest | gzip > iris-images.tar.gz
git bundle create iris-code.bundle --all       # 或者直接打包仓库目录（含 binaries/）

# 目标机
docker load < iris-images.tar.gz
# 解包代码后：python -m venv .venv && pip install -e ".[dev]" --no-index --find-links <wheel目录>
# 或仅用 CLI：pip download -r requirements 侧先行备好 wheel
```

`binaries/` 与 `rules/` 都在版本库内，随代码一起迁移，无需重新下载。`iris-home/` 是运行期目录（数据库、scratch、语料），迁移时**不要**覆盖目标机已有的 `iris-home/`。

## 3. 资产清单与来源

| 文件 | 作用 | sha256 前 16 位 |

| `vmlinux.mipsel.4` / `vmlinux.mipseb.4` | FirmAE 定制 MIPS 内核（含 nvram 插桩） | `7a24ec562c78724f` / `5eac8979c8c66894` |
| `zImage.armel` | FirmAE 定制 ARM32 内核 | `be86180893c412b9` |
| `busybox.{mipsel,mipseb,armel}` | guest 内兜底 shell / 工具 | `b0ac5e9f…` / `879a2980…` / `cee96fc6…` |
| `console.{mipsel,mipseb,armel}` | FirmAE 串口 console 劫持 | `8bb6d414…` / `a0bfb0df…` / `35003996…` |
| `libnvram.so.*` / `libnvram_ioctl.so.*` | NVRAM 用户态仿真 | `61e1897a…` / `3f9e6329…` / `042c8c4f…` 等 |
| `Image.arm64` | Alpine 3.20.10 aarch64 generic virt 内核（6.6.134） | `f8fbdc03e49084b0` |

| `initramfs.arm64` | IRIS 自建 initramfs（见 3.3） | `65606b22fd1ff064` |

MIPS/ARM32 资产来自 FirmAE 发行物；arm64 三项由脚本可复现下载：

```bash
python scripts/emulate/get_arm64_assets.py        # Image.arm64 + busybox.arm64，内置 sha256 校验
```

### 3.2 为什么 arm64 走"通用内核 + initramfs"

FirmAE 没有发布 aarch64 插桩内核。IRIS 的 arm64 通道改用 **Alpine 的 generic virt 内核 + 自建 initramfs**，代价是没有 libnvram / console 劫持（依赖 nvram 的服务起不来，属已知限制），收益是能直接跑起 aarch64 rootfs 的 `/sbin/init`。

针对厂商 init（busybox inittab → `rcS`）不认识 OpenWrt rc.d 的问题，arm64 通道在制作镜像时额外做三件事（`make_image.sh` 的 "Arm64 Generic-Kernel Channel" 段）：把 `iris_net_fix` 直接挂进 `rcS` 后台执行、在 `inittab` 追加 `ttyAMA0::respawn:-/bin/sh` 串口交互 shell、并将 Alpine busybox 放到 `/firmadyne/busybox.arm64` 备用。`iris_net_fix.sh` 本体兼容双调用方式：OpenWrt 下由 `rc.common` 通过 `add_func boot` 注册，直接调用时立即执行修复流程（等 45s → 补 IP → 放行 iptables → `telnetd -p 7002` → goahead/boa Web 兜底），全过程日志写入串口。

### 3.3 重建 `initramfs.arm64`

模块与加载顺序有硬性依赖，改动内核版本后必须重建：

```bash
# 需要 squashfs-tools + cpio，直接在容器里做
docker run --rm -v <项目根>:/w ubuntu:22.04 bash -c \
  "apt-get update && apt-get -y install cpio gzip && bash /w/scripts/emulate/build_arm64_initramfs.sh /w"
```

`scripts/emulate/arm64-initrd/` 存放 initramfs 的种子文件（Alpine busybox、musl 动态加载器、11 个 `.ko`）。这些 `.ko` 取自 `modloop-virt`（Alpine aarch64 netboot 的模块 squashfs）：

```bash
# 提取一次即可（已在仓库中的文件无需重复）
docker run --rm -v <项目根>:/w ubuntu:22.04 bash -c \
  "apt-get update && apt-get -y install squashfs-tools && mkdir -p /m && \
   unsquashfs -d /m/ml <modloop-virt路径> && \
   find /m/ml -name '*.ko' | grep -E 'crc16|crc32c_generic|libcrc32c|mbcache|jbd2|ext4|virtio_mmio|virtio_blk|failover|net_failover|virtio_net'"
```

两个易踩的坑（都已在构建脚本中固化）：

1. `libcrc32c.ko` 依赖 crypto API，必须先 `insmod crc32c_generic.ko`，否则 ext4 模块注册不完整，挂载报 `Cannot load crc32c driver` → `No such file or directory`；
2. initramfs 内的 busybox 是**动态链接**的，必须同时打包 `lib/ld-musl-aarch64.so.1` 并为每个用到的 applet 建符号链接（`mount`/`insmod`/`switch_root`…），否则 `/init` 会以 `error -2` 或 `mount: not found` 静默失败。

`/init` 在 `switch_root` 失败时不再 panic，而是把 `devtmpfs` 的 `/dev`、`/proc`、`/sys` 移入新根后用 `chroot` 执行 `/sbin/init`，最后才退到串口调试 shell。这样即使镜像里的软链有问题（见第 7 节），厂商 init 链依然能跑起来。

## 4. 配置

`.env`（可选，全部以 `IRIS_` 前缀）：

| 变量 | 默认值 | 说明 |
|---|---|---|
| `IRIS_IRIS_HOME` | `iris-home` | 数据/工作目录 |
| `IRIS_DATABASE_URL` | `sqlite:///iris-home/iris.db` | 元数据库；可切 PostgreSQL（`pip install ".[pg]"`） |
| `IRIS_LOG_LEVEL` | `INFO` | structlog 级别 |
| `IRIS_DOWNLOAD_MIRROR` | `https://gh-proxy.com/` | 语料下载代理前缀 |

超时不走配置文件：`iris emulate run --timeout` / API 请求体的 `timeout` 字段逐次指定（默认 120s）。

`rules_dir` 按"当前目录向上找 `rules/` + `src/`"解析，所以 **CLI 与 API 都要在项目根目录启动**，否则 L3 规则静默不生效。

## 5. 冒烟验证

```bash
pytest -q                                   # 128 单测，无需 Docker
iris emulate run <rootfs目录> --arch mipsel --port 8080 --timeout 180
iris emulate run <rootfs目录> --arch arm64  --port 8090 --timeout 600   # aarch64 rootfs，兜底网络修复要 ~5min
curl http://127.0.0.1:8090/                 # Web 可达性
iris emulate stop <iid>
```

`--arch` 会先做 ELF 预检：rootfs 内二进制的主导架构与参数不符时直接拒绝（`arch-mismatch`），避免在内核里 panic 后才报"失败"。预知不匹配可用 `--force` 跳过。

arm64 通道实测样例（Tenda US_TES7002 V1.0re，aarch64 GPL rootfs）：内核与 initramfs 正常挂载 ext4 根 → `switch_root` 被该镜像拒绝（只打印 Usage），`/init` 自动降级为 chroot → 厂商 `/sbin/init` + `rcS` 链跑完 → `iris_net_fix` 补上 `eth0 192.168.1.1`、开 `telnetd:7002`、拉起 goahead；主机侧 `curl -L http://127.0.0.1:<port>/` 返回 **200**（GPON OLT 登录页），`iris emulate run` 两次实测 289s / 258s 判为 success。串口日志里 `goahead: 0: Cannot bind to address *:80, errno 98` 表示厂商自己的 web 已先占了 80，兜底实例退出属正常。

API 形态：`iris serve` 暴露 `/api/v1/{health,firmware,emulate,pipeline}`，其中 `POST /api/v1/pipeline` 接受固件上传→提取→仿真一条龙。

> ⚠️ API 目前**无鉴权**并监听 `0.0.0.0`，只应在隔离网络/本机使用；迁移到公共服务器前需自行加反向代理与认证。

## 6. Windows 宿主注意事项

| 现象 | 原因 / 处理 |
|---|---|
| 容器内脚本语法错误、`$'\r': command not found` | CRLF 污染 `.sh`。仓库已加 `.gitattributes`（`*.sh text eol=lf`）；用 Python 重写脚本时 `open(..., newline="")` |
| `docker run -v` 路径被改写成 `C:\Program Files\Git\...` | Git Bash 的 MSYS 路径转换，命令前加 `MSYS_NO_PATHCONV=1` |
| 中文路径在报错里乱码 | 控制台 GBK。脚本里 `sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding="utf-8", errors="replace")` |
| 根分区符号链接丢失 | NTFS 上打包 rootfs 需 `SeCreateSymbolicLinkPrivilege`；IRIS 已把 rootfs 组装/挂载全部放进容器（见 `make_image.sh`） |
| `pip install` 后仍找不到 `iris` | 虚拟环境未激活，或使用 `python -m iris.cli` |

## 7. 故障速查

| 日志关键字 | 含义 | 处理 |
|---|---|---|
| `Failed to execute /init (error -2)` | initramfs 缺 `/bin/sh` 或 musl 加载器 | 重建 `initramfs.arm64`（3.3） |
| `mount: not found` | applet 符号链接缺失 | 同上 |
| `Cannot load crc32c driver` | 模块顺序错（缺 `crc32c_generic`） | 同上 |
| `Usage: switch_root`（无其它信息） | 新根里 `/sbin/init` 解析不到：Windows 侧暂存 rootfs 丢了 `/sbin -> /bin` 软链，或补建的软链写成了**绝对**目标（绝对路径相对 initramfs 解析）；个别厂商镜像 pivot 本身被拒 | `make_image.sh` 以相对目标 `bin` 重建软链；`/init` 随后自动降级 chroot，厂商 init 仍可启动（见 3.3） |
| `potentially unexpected fatal signal 4` | QEMU CPU 型号不支持二进制用到的指令（如 ARMv8.3 PAC） | 确认 arm64 通道用 `-cpu max` |
| `VFS: Unable to mount root fs on unknown-block(0,0)` | 内核无 rootfs 驱动 | 需 initramfs，或换回 FirmAE 内核架构 |
| `error -8` + `binfmt-464c` | rootfs 架构与 `--arch` 不符 | 用预检给出的正确架构 |
| `IRIS-NETFIX: no interface has an IP, assigning fallback` | 厂商 configd 依赖真实存储（如 `ubi0:ubi_Config`）未获址，IRIS 兜底生效 | 正常；`telnetd` 端口 7002 与 Web 由 netfix 拉起，整机起壳较慢时把 `--timeout` 提到 480 |
| baked 镜像改动不生效 | 忘建镜像 | `docker rmi -f iris-emulate-baked:latest` 后重建 |
