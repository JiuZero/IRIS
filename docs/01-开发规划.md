# 网络设备固件仿真平台开发规划与实践预期

> 面向路由器、IP 摄像头等网络设备的全自动化固件仿真（Firmware Rehosting）平台
> 本文档基于：① 学术文献与 2025–2026 前沿动态调研；② 对 FirmAE、firmadyne、FirmWire、HALucinator 四个开源项目的**源码级分析**（项目已克隆至本工作区 `research/` 目录）
> 撰写日期：2026-09-26

---

## 1. 执行摘要

"仿真网络设备"在学术界称为固件 Rehosting（重宿主）：将厂商固件镜像在 QEMU 等模拟器中还原为可交互、可分析的"虚拟设备"。经过十年演进（Avatar → firmadyne → FirmAE → FirmPilot），这条路线已被证明**可行且工程上可规模化**，但不存在"完美仿真"的银弹——现有最好方案在大规模真实语料上的网络可达率仍停留在 40%~72% 区间，且强依赖持续的环境恢复工程。

**核心结论（一句话版）**：以 QEMU 全系统仿真 + 定制内核插桩 + NVRAM 用户态仿真（FirmAE 路线）为骨架，以"自动仲裁 + LLM 辅助环境恢复"为差异点，以摄像头媒体面与多设备组网为特色场景，分 6 个里程碑（约 9–12 个月，3–5 人团队）达到：
- 主流路由器固件 Web 可达率 ≥ 80%（对标 FirmAE 论文基准 79.36%）；
- 大规模长尾语料可达率 ≥ 60%（对标 FirmPilot 2026 结果 52.39% 并超越）；
- 摄像头固件支持 RTSP/ONVIF 服务可交互仿真（业界尚无开源自动化标杆）。

## 2. 领域全景与文献综述

### 2.1 学术技术脉络（三代路线）

| 代际 | 代表工作 | 核心思想 | 局限 |
|---|---|---|---|
| 第 0 代：框架期 | **Avatar**（NDSS 2014）；Costin et al. 大规模固件静态分析（USENIX Sec 2014） | QEMU 与真实硬件混合执行；证明固件大规模分析价值 | 依赖真机，无法纯虚拟化 |
| 第 1 代：Linux 全系统仿真 | **firmadyne**（NDSS 2016）；**FIRM-AFL**（USENIX Sec 2019） | QEMU 跑定制 MIPS 内核 + libnvram 用户态 NVRAM 仿真 + 网络自动推断 | 成功率仅 ~16–24%，NVRAM/网络是最大瓶颈 |
| 第 1.5 代：仲裁工程化 | **FirmAE**（ACSAC 2020，DOI 10.1145/3427228.3427294） | 五大仲裁技术（Boot/Network/NVRAM/Kernel/ETC），1,124 个路由器+摄像头固件成功率 16.28% → **79.36%**，挖出 12 个 0-day 影响 23 款设备 | 换到大规模新语料后可达率回落（见 2.3） |
| 第 2 代：MCU/裸机仿真 | **P2IM**、**HALucinator**（USENIX Sec 2020）、**uEmu**（USENIX Sec 2021）、Spec-Imitator（S&P 2022） | 不仿真真实外设：P2IM 按外设接口访问建模；HALucinator 在 HAL 库函数入口断点拦截（HLE）；uEmu 符号执行推断外设响应规则 | 只适用 MCU/RTOS 固件，不覆盖嵌入式 Linux |
| 第 2 代：无 OS 协处理器 | **FirmWire**（NDSS 2022）、Frankenstein（USENIX Sec 2020） | avatar2+PANDA 动态构建内存映射，Python 级 MMIO 外设，基带/蓝牙固件仿真+模糊测试 | 逐芯片厂商适配成本高 |
| 第 3 代：智能环境恢复（2025–2026 前沿） | **FirmPilot**（arXiv 2607.14903）、**Pemu**（CCS 2025）、RPM/Bluezz（arXiv 2608.29737） | FirmPilot：证据引导的多智能体（LLM agent）迭代重建启动/持久状态/网络三要素；Pemu：协议感知封包生成打通深层协议栈；RPM：把外设建模为反应式状态机（中断×MMIO×DMA 联动） | Agent 方法存在不可复现风险，需"证据+执行验证"约束 |

### 2.2 开源/商用工具全景

| 工具 | 定位 | 对本项目的参考价值 |
|---|---|---|
| **firmadyne** | Linux 路由器固件仿真鼻祖 | 流水线雏形；网络推断内核日志锚点思路 |
| **FirmAE** | firmadyne 工程化后继（本文主要解剖对象） | 五大仲裁技术完整实现，可直接借鉴/移植 |
| **HALucinator** | MCU 固件 HAL 层拦截式仿真 | 摄像头 MCU 子系统（云台/ISP）与 shim 泛化思想 |
| **FirmWire** | 基带固件仿真 | Python 外设框架、快照锚定 fuzz 工作流 |
| **unblob**（OneKey） | 现代固件解包框架，替代 binwalk 3.x | 提取层首选，格式覆盖广、易扩展 |
| **EMUX（原 ARM-X）** | 半自动 ARM 路由器仿真训练平台 | 人工修复样本的"标准答案库"参考 |
| Renode（Antmicro） | MCU/SoC 全仿真+多节点组网 | 非设备级 Linux 场景、板级外设模型 |
| EMBA / FACT | 固件静态分析平台 | 可作为仿真前置筛查与 CVE 关联的配套 |
| Firmware Analysis Toolkit（FAT） | firmadyne 封装 | 交互体验参考（价值低） |

### 2.3 对"成功率"的冷静认知（重要）

- FirmAE 官方基准：1,124 固件，Web 可达 **79.36%**；
- FirmPilot（2026）在更大的 **LFwC 真实语料**上重测：FirmAE 的 Web 可达率仅 **25.49%**、网络可达 **39.30%**；FirmPilot 用多智能体环境恢复提升至 **52.39% / 71.93%**，平均每固件检出服务 0.86 → 1.62。
- **结论**：① 论文基准是精选语料，换到脏语料成功率会大幅下降；② "环境恢复自动化"（而非执行引擎）是当前最大的技术增量空间；③ 我们的规划必须把失败分类、自动修复环、人工样本库作为一等公民。

## 3. 核心项目代码剖析（源码证据）

四个项目已克隆至 `research/{FirmAE, firmadyne, FirmWire, halucinator}`，以下结论均出自本次源码走读（行号对应仓库当前内容）。

### 3.1 FirmAE 端到端流水线（本项目的主参考）

```
固件包 ──▶ [1] 提取 sources/extractor/extractor.py (binwalk 封装, run.sh:107-124)
            │    rootfs 判定: 命中≥4个UNIX标准目录 (extractor.py:29-31,145-178)
            │    固件头精切: uImage/TRX/TP-Link 偏移表 (extractor.py:529-632)
            ▼
       [2] 架构识别 scripts/getArch.py (MIPS大/小端, ARM) + inferKernel.py (提取 init= 启动链)
            ▼
       [3] 磁盘构建 scripts/tar2db.py + makeImage.sh
            │    1GB ext2 磁盘 + chroot 内 inferFile.sh(推断 init 链/web服务) + fixImage.sh(修补)
            ▼
       [4] 网络推断 scripts/makeNetwork.py (核心, 898行)
            │    试跑 TIMEOUT 秒 → 解析内核日志 5 个锚点:
            │      __inet_insert_ifa / inet_bind / SIOCSIFHWADDR / br_add_if / register_vlan_dev
            │    → 输出 (ip, dev, vlan, mac, brif) 五元组 → 网络类型分类仲裁
            ▼
       [5] guest 运行时 preInit.sh → network.sh → run_service.sh (web 服务保活看门狗)
            │    NVRAM: libnvram.so 经定制内核 LD_PRELOAD 注入所有进程
            ▼
       [6] 判定 check_emulation.sh: curl http/https 可达即成功; 失败写 result 分类字符串
```

### 3.2 五大仲裁技术——FirmAE 成功率提升的本质（必须吃透）

| 仲裁 | 代码位置 | 机制精髓 | 对新平台的启示 |
|---|---|---|---|
| **NVRAM** | `sources/libnvram/`（nvram.c, alias.c, config.h） | ① 编译为 `-shared -nostdlib` 动态库，借宿调用进程 C 运行库，兼容 uClibc/glibc；② 内核改 `init/main.c` 自动 `LD_PRELOAD`；③ **未命中 key 返回空串而非 NULL**（nvram.c:393-417）避免崩溃；④ 厂商 API 别名层：Broadcom/Realtek apmib/Netgear acosNvramConfig/ZyXel envram/Ralink 等（alias.c）；⑤ **四级默认值瀑布**：内置表 → 固件自带 default 文件 → **inferDefault.py 动态推断闭环**（解析日志中全部被查询的 key，在 rootfs 中找出"包含超半数 key 的文件"回注，inferDefault.py:35-53）→ override 覆盖目录 | NVRAM 是第一成功率杠杆；默认值"日志→文件→回注"闭环值得原样复刻，并可用静态数据流/LLM 增强推断 |
| **Network** | `scripts/makeNetwork.py:635-741` | 产出 5 种 network_type（normal/reload/bridge/bridgereload/default）+ 双注入通道：内核态 tap 直连（宿主 IP = guest IP 末位±1）vs 用户态 slirp + hostfwd 端口转发；DHCP 段过滤；guest 侧 network.sh 按 type 修复网桥/清 iptables | "分类降级 + 双通道"可直接移植；失败网络类型自动降级策略是免人工的关键 |
| **Boot** | `scripts/inferFile.sh`, `fixImage.sh:13-50` | **不模拟 bootloader**，改为"init 链仲裁"：合并固件内核期望的 init 程序列表 + 根目录 /init + preinit/rcS 搜索，修复失效符号链接后写入 `/firmadyne/init` 逐条重放 | 放弃 bootloader 保真换取规模；init 链自动重建是必要能力 |
| **Kernel** | 内核为独立预编译仓库（FirmAE_kernel-v2.6/v4.1），支持 2.6/4.1 双版本 + ARM | 内核级：网络日志锚点 printk、LD_PRELOAD 注入、execve 计数（第 4 次 execve 拉起 console）、`firmadyne.syscall` 全量 syscall 日志；libnvram 内核态 shim 拦 Netgear `agApi_fw*` 死循环 | 内核 fork 是长期维护负担 → 新平台应收敛到单一内核版本 + QEMU TCG plugin 承担插桩（见 §5.3） |
| **ETC** | `firmae.config:3-15`, `run_service.sh` | 超时加倍、web 服务主动探测优先级（uhttpd→httpd→goahead→alphapd→boa→lighttpd）、静态 busybox 补 /dev、删 reboot 防自我重启、`/dev/gpio/in` 喂 watchdog、服务进程 10 秒级拉活 | 杂项修补清单是工程血泪，应固化为"修补策略库"并做成可插拔规则 |

**失败分类现状**（仅 4 类：extraction fail / get arch fail / not valid arch / false）过于粗糙——新平台应把 network_type、NVRAM key 数量、init 阶段日志等中间信号纳入结构化失败画像（这是 LLM 修复环的输入）。

### 3.3 三条路线横向对比

| 维度 | FirmAE/firmadyne | HALucinator | FirmWire |
|---|---|---|---|
| 目标固件 | 嵌入式 Linux（MIPS/ARM） | MCU 裸机/RTOS（Cortex-M） | 无 OS 基带/协处理器 |
| 执行底座 | 发行版 QEMU + 定制内核 | avatar2 + avatar-qemu（TCG） | avatar2 + PANDA（QEMU fork） |
| 外设策略 | 尽量不碰（内核容忍缺硬件） | **HAL 函数断点拦截**（intercepts.py:100-157，YAML 配置地址，返回跳板注入返回值，main.py:37-80 写 Thumb `BX LR`） | **Python 级 MMIO 外设框架**（peripheral.py，含 CyclicBit 骗状态轮询），内存映射按固件 MPU/TOC 表动态重建（loader.py:108-330） |
| 拦截抽象层级 | 用户态 API 别名（LD_PRELOAD） | QEMU 地址级断点 | 指令/基本块级 hook |
| 对本项目价值 | **主干** | 摄像头 MCU 子系统；主线卡死时的"shim 旁路"方法论 | 快照/fuzz 工作流；闭源协处理器固件应对范式 |

**互补结论**（直接引用本次代码分析）：一条 Linux 主线解决"量"；HAL 拦截解决"Linux 之外的 MCU 层"；Python 外设框架解决"无 OS 闭源协处理器"。拦截抽象依次下沉：libnvram（库级）→ HALucinator（地址级）→ FirmWire（寄存器/指令级）。典型组合：主线批量跑主固件 → 失败样本按失败阶段分流 → 私有 HAL 用 shim 旁路，协处理器/裸机部件单独 rehost。

## 4. 技术难点与失败模式清单

基于 FirmAE 失败分类 + FirmPilot 在 LFwC 语料上的回落数据，失败模式按阶段归纳：

| 阶段 | 失败模式 | 现有对策 | 仍需突破 |
|---|---|---|---|
| 提取 | 加密/非标准打包（企业级固件）、Yocto 分区 | unblob + binwalk 双引擎 | 加密固件需配合获取渠道（UART/SPI dump），超出纯软件边界 |
| 架构 | x86/PowerPC/ARM64 固件（FirmAE 仅支持 armel/mipseb/mipsel，firmae.config:37-56） | 限流提示 | 扩 ARM64 内核支持是低垂果实 |
| 启动 | 非 Linux 内核（VxWorks、私有 RTOS）、init 死锁 | init 链仲裁 | RTOS 类走 HALucinator/Renode 路线，主线标注不可仿真 |
| NVRAM | 默认值全缺失、flash 型持久存储、私有 IPC 型 nvramd | 四级瀑布 + 空串兜底 | 静态数据流分析/LLM 推断默认值；持久化语义仿真 |
| 网络 | 网口与 SoC 强耦合（MDIO/交换芯片驱动）、双网桥 WAN 冲突、6in4/PPPoE WAN 侧依赖 | 5 类降级 + 双通道注入 | 摄像头常无 Web 端口、仅 RTSP——成功判定需要协议扩展 |
| 外设 | 摄像头 ISP/sensor、GPIO 按键、LED、eeprom | watchdog 喂狗 + reboot 黑名单 | v4l2 虚拟设备注入（`v4l2loopback` + ffmpeg 推流）可让媒体面活起来 |
| 服务 | 首次开机向导锁定（netgear/asus/dlink） | headless Chrome 自动跳过（initializer.py） | 扩大向导自动化覆盖 |
| 验证 | "Web 可达"≠"行为正确"，与真机行为漂移 | ping/web 时延记录 | 需建立真机对照集（ differential testing） |

## 5. 目标系统设计

### 5.1 设计目标与非目标

**目标**：
1. 端到端全自动：固件包输入 → 虚拟设备网络服务可达输出，全程无人值守，失败自动分类归因；
2. 多设备类型：无线路由器（MIPS/ARM）为第一梯队，IP 摄像头（Web + RTSP/ONVIF 媒体面）为第二梯队；
3. 可交互：宿主可直接访问仿真设备的管理面/数据面，支持 gdb/socat/快照恢复，可对接 fuzzing；
4. 规模化：容器化并行 ≥ 100 实例，千级固件/天吞吐；
5. 演进式：失败样本进入"环境恢复规则库 + LLM 修复环"，成功率随语料增长单调提升。

**非目标（M2 前）**：逐条指令级硬件保真、bootloader 精确模拟、加密/签名固件的自动解密、非 Linux RTOS 全覆盖。

### 5.2 总体架构（五层）

```
┌─────────────────────────────────────────────────────────────────┐
│ L5 编排层  REST API / CLI / Web 控制台                           │
│   任务队列(Celery/RQ) · Docker 并行调度 · 结果看板 · 失败分类报表  │
├─────────────────────────────────────────────────────────────────┤
│ L4 交互与分析层                                                   │
│   网络接入(tap/slirp+hostfwd) · 快照恢复 · gdb stub · socat      │
│   Web fuzzer(命令注入/BOF) · 协议感知 fuzz 接口 · RTSP/ONVIF 测试  │
├─────────────────────────────────────────────────────────────────┤
│ L3 环境恢复层（核心创新区）                                        │
│   规则引擎(修补策略库: 30+ 条 FirmAE 式规则, 可插拔)               │
│   NVRAM 服务(四级默认值瀑布 + 厂商 alias + 静态/LLM 推断闭环)      │
│   网络仲裁器(5 类降级) · init 链仲裁 · 失败画像收集 → LLM 修复环   │
├─────────────────────────────────────────────────────────────────┤
│ L2 执行层                                                         │
│   QEMU fork (malta/virt/realview 机器)                           │
│   定制内核 fork (4.1/5.x LTS: 网络锚点 printk + LD_PRELOAD 注入    │

│   libnvram.so (-nostdlib) · console · busybox · gdbserver        │
├─────────────────────────────────────────────────────────────────┤
│ L1 提取与识别层                                                   │
│   unblob + binwalk 双引擎 · rootfs 判定(UNIX 目录阈值法)          │
│   固件头精切(uImage/TRX/TP-Link/Broadcom) · 架构识别 · 内核版本探测│
│   元数据库(brand/image/object/object_to_image/product 五表继承)   │

```

### 5.3 关键技术选型（与 FirmAE 的差异点即创新点）

| 组件 | 选型 | 理由与差异点 |
|---|---|---|
| 解包引擎 | **unblob 为主、binwalk 兜底** | unblob（OneKey 开源）格式覆盖与维护性优于 binwalk；两者结果合并取并集，rootfs 判定沿用"≥4 个 UNIX 目录"阈值法并加入（/etc/init.d 存在性 + busybox ELF）加权 |
| QEMU | 基于 **QEMU ≥ 7.x 独立 fork** | FirmAE 直接用发行版 QEMU 但内核停在 4.1；我们用新 QEMU + TCG plugin API 做 MMIO/执行流插桩（不需重编译内核即可监控外设访问），内核锚点仅保留网络推断 5 个 printk（补丁小、可随 LTS 滚动） |
| 内核 | 单一 **5.x LTS fork**（MIPS BE/LE + ARM32 + 预留 ARM64） | 摒弃 FirmAE 双内核版本维护；对 2.6 时代老固件用兼容开关处理 |
| NVRAM | **移植 FirmAE libnvram**（`-nostdlib` 共享库方案）+ 增强 | 该方案是 16.28%→79.36% 的最大单点功臣，语义已被验证；增强：① `nvram_get` 未命中时先查"跨固件共享 key 值统计库"（同厂商同型号系列规律），再回退空串；② LLM 辅助：把失败样本的 NVRAM key 列表 + rootfs 上下文交给 LLM 提议默认值候选，经"执行验证"后入库（借鉴 FirmPilot 的 evidence-guided 原则，杜绝不可复现修改） |
| 环境恢复 | **规则引擎（确定性） + LLM 修复环（探索性）双轨** | 规则库：fixImage.sh/makeNetwork.py 的全部策略固化为 YAML 规则（可插拔、可消融实验）；LLM 环：仅在规则穷尽后介入，每步修改必须有执行证据（内核日志/服务探活），修改产物可回放 |
| 摄像头支持 | **v4l2loopback + GStreamer 推流 + RTSP 探测** | 内核侧注入虚拟视频源使 ISP/v4l2 栈不空转；成功判定扩展为 HTTP ∪ RTSP ∪ ONVIF GetProfiles 探测；这是相对 FirmAE 的空白区增量 |
| 失败画像 | 结构化 JSON（阶段/信号/日志指纹/网络类型/NVRAM 统计） | 替代 FirmAE 4 类字符串；是修复环与看板的统一数据底座 |
| 存储 | PostgreSQL（沿用 firmadyne 五表 schema + 新增 `emulation_run`、`failure_profile`、`repair_action` 表） | firmadyne 的 object 去重设计（跨固件文件复用）已验证好用 |
| 协处理器预留 | 提供 Renode/Avocado 适配器接口 | 摄像头云台 MCU、WiFi 协处理器等，M4 后按需启用 |

### 5.4 差异化定位（为什么不直接 fork FirmAE）

| 现有方案短板 | 本平台对策 |
|---|---|
| FirmAE 语料泛化差（LFwC 上 Web 可达 25.49%） | LLM 修复环 + 结构化失败画像，主打长尾鲁棒性 |
| 无摄像头媒体面仿真 | v4l2 虚拟注入 + RTSP/ONVIF 面探测与测试 |
| 单机、无组网 | 容器编排 + **多设备虚拟组网实验场**（多台虚拟设备 + 攻击机 + 控制器拓扑，用 Linux bridge/VXLAN 连通），支撑横向攻击与联动测试 |
| 失败原因黑盒 | 全链路失败画像与归因报表 |
| 内核双版本维护包袱 | 单 LTS 内核 + QEMU plugin 分担插桩 |
| 修补策略散落 shell | 策略库化、可插拔、可回归测试（每个规则对应样例固件回归集） |

## 6. 分阶段路线图（3–5 人团队，约 9–12 个月）

| 里程碑 | 周期 | 交付物 | 验收标准 |
|---|---|---|---|
| **M0 技术验证** | 2 周 | 部署原生 FirmAE，跑通 10 款公开路由器固件；选定 50–100 款自建评测集（覆盖 mipseb/mipsel/armel + D-Link/TP-Link/Netgear/Tenda/海康/大华） | 团队对失败模式建立一手认知；评测集与 baseline 数字落库 |
| **M1 MVP 主干** | 6–8 周 | L1 提取层（unblob+binwalk 合并）+ L2 执行层（内核 patch、libnvram 移植、malta/virt 机型）+ 网络仲裁器 v1 + Web 可达判定 | 评测集 Web 可达率 **≥ 60%**；单固件端到端 ≤ 10 分钟 |
| **M2 规模化** | 6 周 | Docker 并行 ≥ 50 实例；NVRAM 推断闭环 + 厂商 alias 扩充；修补策略库 v1（30+ 规则）；失败画像 v1；摄像头 Web 面支持 | 评测集 **≥ 80%**（对标 FirmAE 论文）；错误分类覆盖 8 类失败模式 |
| **M3 交互与分析** | 8 周 | 快照/恢复；gdb/socat 调试工具链；Web fuzzer（移植 fuzzer.py 思路：CGI/HNAP/表单信息提取 + 探针喷洒 + execve 日志回捞验证）；v4l2loopback + RTSP/ONVIF 面仿真；REST API | 在 ≥ 3 款仿真设备上完成一次全流程 fuzz 并产出可复现崩溃报告；摄像头媒体面 RTSP 可交互 |
| **M4 智能环境恢复** | 8–12 周 | LLM 修复环（失败画像 → 候选动作 → 执行验证 → 规则沉淀）；跨固件 NVRAM 知识库；大规模脏语料（数百级）批量回归 | 自建大规模语料 Web 可达 **≥ 60%**、网络可达 **≥ 70%**（对标并超越 FirmPilot）；修复动作 100% 可回放 |
| **M5 产品化** | 持续 | 多设备虚拟组网实验场；Web 控制台与报表；CI 集成（固件入库自动仿真+CVE 关联）；开源版/内部版发布 | 一个由 ≥ 5 台虚拟设备 + 客户端组成的示范场景稳定运行 72 小时 |

**团队配置建议**：2 名系统工程师（QEMU/内核/驱动，负责 L2）、1–2 名分析工程师（提取/环境恢复/fuzzing，负责 L1/L3）、1 名平台工程师（编排/API/前端，负责 L5）。M1 起每周跑全量评测集回归，成功率曲线纳入例会。

## 7. 实践预期（量化基准与风险）

### 7.1 成功率预期（基于公开数据外推）

| 指标 | FirmAE 论文 | FirmPilot（LFwC 脏语料） | 本平台预期 |
|---|---|---|---|
| 精选评测集 Web 可达 | 79.36% | — | M2 ≥ 80%，M4 ≥ 85% |
| 大规模长尾语料 Web 可达 | 25.49% | 52.39% | M4 ≥ 60% |
| 大规模长尾语料网络可达 | 39.30% | 71.93% | M4 ≥ 72% |
| 每固件平均检出服务 | 0.86 | 1.62 | ≥ 1.8（含 RTSP/ONVIF 面） |
| 摄像头固件可达率 | 无公开基准 | 无公开基准 | 首个系统基准（预期 50–65%，属行业空白贡献） |

### 7.2 性能与吞吐预期

- 单固件 check 流程（提取→试跑→判定）：3–10 分钟（FirmAE TIMEOUT=240s ×2 + 提取）；M2 后目标中位 5 分钟；
- 100 容器并行：约 **1,500–3,000 固件/天**（按 8h × 并发 × 中位耗时 50% 有效占比估算）；
- 仿真实例启动后常驻内存 256MB–1GB/实例（视固件 rootfs 大小）。

### 7.3 主要风险与缓解

| 风险 | 概率/影响 | 缓解 |
|---|---|---|
| LLM 修复环产生不可复现的镜像修改 | 中/高 | 借鉴 FirmPilot：每步动作必须绑定执行证据，产物可回放；规则沉淀后走确定性通道 |
| 内核/QEMU fork 维护成本膨胀 | 中/中 | 锚点补丁最小化（5 个 printk）；插桩尽量走 QEMU plugin；锁 LTS 版本 |
| 摄像头 ISP/协处理器无法仿真 | 高/中 | 明确边界：仅保证 Linux 主 SoC 的 Web+RTSP 面可达；MCU 子系统走 Renode/HAL 拦截预留接口 |
| 加密固件无法提取 | 中/低 | 与硬件侧（UART/SPI dump）流程协同；平台内标注原因 |
| 评测集版权 | 低/中 | 内部评测集自建 + 引用公开语料（LFwC 等）时遵守许可 |
