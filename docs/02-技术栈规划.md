# IRIS 技术栈规划

> 版本：v0.1（2026-09-26）｜对应架构：docs/01-开发规划.md §5.2 五层架构（L1–L5）
> 选型原则：① 与 FirmAE 验证路线兼容，可平滑移植其已验证组件；② 优先选择活跃维护的现代工具链；③ 每项选型给出备选与切换成本。

## 1. 选型总览

| 层 | 组件 | 选型 | 语言/形态 | 备选方案 |
|---|---|---|---|---|
| L1 提取识别 | 解包引擎 | **unblob**（主）+ binwalk（兜底）+ sasquatch | Python / C | 自研 binwalk 3.x 插件 |
| L1 提取识别 | 文件识别 | libmagic（python-magic）、pyelftools | Python | — |
| L2 执行 | 虚拟机 | **QEMU fork ≥ 7.2**（mips/mipsel/arm-softmmu；malta/virt 机型；TCG plugins） | C | 沿用发行版 QEMU（起步期） |
| L2 执行 | 客户内核 | **Linux 5.15 LTS fork**（网络锚点 printk + LD_PRELOAD 注入 + execve 计数 + syscall 日志） | C | 4.1 内核（老固件兼容开关） |
| L2 执行 | NVRAM 库 | **libnvram（移植 FirmAE）**：C11、`-shared -nostdlib`、四级默认值瀑布 | C | 内核模块形态（不推荐） |
| L2 执行 | 容器与并行 | **Docker ≥ 24 + Docker Compose**，容器内运行单实例仿真 | — | podman（合规场景） |
| L2/L4 媒体面 | 摄像头注入 | **v4l2loopback-dkms + GStreamer/ffmpeg 推流** | C / CLI | 内核 v4l2-dummy 驱动 |

| L4 交互分析 | 网络接入 | Linux bridge/tap（内核态）+ slirp/hostfwd（用户态）双通道 | CLI | — |

| L5 编排 | API 服务 | **FastAPI + uvicorn** | Python | Flask（不推荐） |
| L5 编排 | 任务队列 | **Celery + Redis**（仿真任务异步化、百级并发） | Python | RQ（更轻，M1 可先用） |
| L5 编排 | 元数据库 | **PostgreSQL 15**（继承 firmadyne 五表 schema + emulation_run/failure_profile/repair_action 新表） | — | SQLite（单机开发期） |
| L5 编排 | ORM/迁移 | SQLAlchemy 2.x + Alembic | Python | — |
| L5 可观测 | 日志与指标 | structlog（JSON 日志）+ Prometheus + Grafana（可选） | Python | — |
| L5 前端（M5） | 控制台 | **Vue 3 + TypeScript + Vite + Element Plus** | TS | React + Antd |
| 质量保障 | 测试/静态检查 | **pytest**、ruff、mypy、pre-commit、coverage.py | Python | — |
| 质量保障 | CI | pre-commit（本地强制）+ GitHub Actions / Gitea Actions（可选） | YAML | Jenkins |

## 2. 语言与运行时约束

| 语言 | 用途 | 版本约束 | 说明 |
|---|---|---|---|
| Python 3.11+ | L1/L3/L4/L5 全部编排与恢复逻辑 | ≥ 3.11（性能提升 + tomllib） | 唯一胶水语言，禁止引入第二脚本语言 |
| C (gcc ≥ 12) | libnvram、内核补丁、QEMU 插件 | 与内核/QEMU 工具链一致 | libnvram 必须保持 `-nostdlib`、无 glibc 依赖 |
| Shell (POSIX bash) | guest 内脚本（preInit/network/run_service）、镜像构建 | bash ≥ 4.2 | 沿用 FirmAE 风格，便于直接移植 |
| Rust（远期可选） | 高性能提取引擎（如需替换 unblob 热路径） | 暂不引入 | 避免过早优化 |
| TypeScript | 前端控制台（M5 才启动） | ≥ 5.x | 严格模式 |

## 3. 关键依赖的移植与维护策略

1. **QEMU fork**：起步期直接用发行版 QEMU + TCG plugin（不改源码）；当确需设备模型改动（如摄像头 ISP 外设）时再 fork，fork 必须以 patch 队列形式管理（`qemu/patches/*.patch`），禁止散改；
2. **内核 fork**：仅保留 4 类最小补丁——网络推断 5 锚点 printk（`__inet_insert_ifa/inet_bind/SIOCSIFHWADDR/br_add_if/register_vlan_dev`）、`init/main.c` LD_PRELOAD 注入、execve 计数器、syscall 日志开关；跟随 5.15.x 稳定分支滚动 rebase；
3. **libnvram**：从 FirmAE `sources/libnvram` 移植后，新增：跨固件 NVRAM 知识库查询接口、LLM 提议默认值的"候选→执行验证→入库"通道；厂商 alias 表独立为 `alias_*.c` 按厂商分文件；
4. **unblob/binwalk 并用**：两者提取结果取并集后用统一 rootfs 判定器打分（UNIX 目录阈值 + busybox ELF 加权），避免单引擎漏检；
5. **LLM 依赖隔离**：LLM 仅出现在 L3 修复环与 L5 报表摘要两处，通过 `iris.llm` 单一模块封装，任何其余代码不得直接 import SDK——保证可整体切换模型供应商或完全关闭（确定性模式）。

## 4. 数据模型与存储布局

```
PostgreSQL:  brand / image / object / object_to_image / product   （firmadyne 兼容五表）
             emulation_run   # 每次仿真尝试：iid、阶段耗时、network_type、判定结果
             failure_profile # 结构化失败画像：阶段/信号/日志指纹/NVRAM统计（JSONB）
             repair_action   # 修复动作账本：来源(规则/LLM)、证据、是否沉淀为规则
文件系统:     images/  QEMU 磁盘与内核   scratch/  每次运行的工作目录与日志
             corpus/  固件语料（不入库大文件，仅记录哈希与元数据）
```

## 5. 工程规范（强制）

- **Git 纪律**：每个任务推进必须留下可回滚的 commit 节点；Conventional Commits；里程碑打 tag（`m0-baseline`、`m1-mvp`…）；大改动拆多个原子 commit；
- 分支模型：`main` 为可运行基线，日常开发在 `feature/<topic>`，合并前必须通过 `pytest + ruff + mypy`；
- 每条修补规则（rules/*.yaml）必须附带至少一个回归样例固件（记录哈希），CI 中批量回归成功率不许倒退；
- 评测集全量回归脚本每周运行，成功率曲线写入 `docs/eval-log.md`。
